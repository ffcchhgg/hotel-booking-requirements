# 设计工作资料：架构与边界

状态：AI 辅助设计候选，待学生审阅。实验二为设计与建模，尚未实现后端或完成业务验收。

## 1. 基线与范围

- 项目：南京大学校内多酒店预订系统。酒店示例用“示例酒店 A/B”，不擅自补充实际酒店名称。
- 需求基线：实验一 `lab1-final`；28 条需求，19 条已确认、9 条待确认。
- 三类角色：顾客、所属酒店工作人员、平台管理员。工作人员不是跨酒店超级用户，管理员不是默认具备所有业务写权限。
- 资金：仅模拟付款与退款；电话联系与公安备案均在系统外。
- 本次设计覆盖核心模块与异常路径；不扩展会员、积分、优惠券、第三方平台同步或真实支付。

## 2. 候选架构

采用模块化单体。表示层 → 应用服务 → 领域规则与数据访问 → 关系数据库。自动任务通过应用服务调用业务能力，不绕过业务校验直接修改订单。

| 编号 | 模块 | 职责与主要接口候选 | 不应承担的职责 |
| --- | --- | --- | --- |
| M01 | 身份与授权 | 注册、登录、会话、资源范围校验 | 从请求参数直接采信角色或酒店归属 |
| M02 | 酒店资料与审核 | 酒店房型资料、版本、申请、审核 | 审核过程中直接修改历史订单价格 |
| M03 | 库存与报价 | 逐夜可售、报价快照、占用释放、停售 | 用具体房间清洁状态代替逐夜库存 |
| M04 | 订单协调 | 创建、确认、取消、修改、状态校验 | 直接信任客户端金额与旧状态 |
| M05 | 模拟款项 | 付款、原账户退款、款项流水 | 调用真实支付、孤立提交退款 |
| M06 | 前台接待 | 线下订房、身份核验、分房、入住退房、清洁 | 入住时重复扣预订房量 |
| M07 | 自动任务与应急 | 超时、未到店结束、故障影响处理 | 绕开订单状态机或恢复故障房源销售 |
| M08 | 查询与统计 | 权限内订单检索、明确口径的聚合 | 将管理员查询权限扩大为修改权限 |
| M09 | 操作记录 | 成功业务日志、失败安全事件、查询 | 保存明文密码、完整身份证或整份请求体 |

表示层按顾客、工作人员、管理员提供不同导航；同一模块可供多个角色调用。基础设施包括关系数据库、时钟、事务管理与模拟支付适配器。模块划分不是独立微服务部署要求。

## 3. 交互与事务

### 接单

授权 → 幂等键及版本检查 → 取得库存竞争域锁 → 重新读取订单和各入住夜 → 检查超时及竞争优先级 → 整体占用全部夜数 → 改为已确认 → 写业务日志 → 一次提交。

无房分支：保持无占用，取消并全额模拟退款；明确受影响的其他待接单订单，在同一受控业务处理内重新核验，不能按房型粗暴取消所有日期订单。

为避免跨夜多锁死锁，初期实现候选使用同一酒店的库存协调锁；同一订单的所有房型属于同一酒店，受影响订单也在该锁内重读。订单状态、取消、审核、应急及库存竞争操作均遵循统一锁序。该方案牺牲同酒店写操作的并发度，便于课程原型保证正确性；后续优化必须保持相同业务不变量。

### 取消

授权 → 竞争域锁 → 重读状态与服务端时间 → 计算取消原因和退款额 → 仅释放仍有效的预订占用 → 模拟退款流水 → 订单终态 → 日志 → 一次提交。

### 修改

先验证新申请结构并生成带版本的报价；展示原单退款、新单费用和失去原房风险。提交后执行“原单取消”这一事务，再进入新申请及付款流程。原单取消已成功而新单业务失败，不恢复原单。通过修改请求记录保存进度，重试继续未完成步骤，不重复取消或创建新单。报价确认后、取消前若原状态或退款额变化，重新提示，而不是静默执行。

### 审核

申请保留变更前版本、拟变更内容、发起人和审核结果。审核通过前再次验证当前版本、有效占用及业务权限；提交时合法不代表生效时仍合法。审批结果、资料或库存价格版本、日志同事务提交。冲突时保持旧生效版本。

### 自动任务

数据库保存待处理订单及期限。周期扫描只是唤醒方式，业务期限仍为付款后 30 分钟；接单入口也必须检查期限，防止扫描延迟让超时单被接。失败任务可重试，补扫使用相同业务服务。设计目标是在到期后尽快处理，实际调度延迟需要后续实现测量，不能宣称精准实时执行已验证。

## 4. 持久化候选

| 对象 | 关键数据与关联 | 约束候选 |
| --- | --- | --- |
| Account | 登录标识、密码哈希、角色、工作人员所属酒店 | 登录标识唯一；顾客注册不能赋权 |
| Hotel / RoomType | 酒店、校区、房型设施、容量、审核版本 | 房型必须归属酒店；历史引用不能孤立 |
| InventoryDay | 房型、住宿日期、可售容量、停售、版本 | 房型+日期唯一；容量非负 |
| RateDay | 房型、日期、公开价、在线价、版本 | 金额以整数分表示；来源与舍入见假设 |
| Booking / BookingItem | 渠道、顾客或线下联系人、日期、状态、数量 | 订单唯一；在线顾客必填；数量正整数 |
| BookingNightPrice | 明细、住宿日期、数量、成交单价、折扣 | 保存成交快照；不被后续改价覆盖 |
| InventoryAllocation | 订单明细、日期、占用数量、释放标记 | 占用与释放可追溯；仅释放一次 |
| Payment / Refund | 订单、金额、原付款账户、原因、请求键 | 退款关联成功付款；累计退款不超实付 |
| PhysicalRoom | 酒店、房型、房号、当前接待状态 | 酒店内房号唯一 |
| Stay / GuestRegistration | 订单、房间、入住退房时间、全部入住人 | 当前房间不能被两个有效入住同时占用 |
| ChangeRequest | 目标、基线版本、拟变更、审核人、结果 | 未审核资料不对外生效 |
| ModificationRequest | 原单、新申请、新单、步骤、请求键 | 一个修改请求只能形成一个后继新单 |
| Incident | 酒店、房型、日期、影响清单、处置进度 | 封停售与释放占用分开保存 |
| FeePolicy / FeeCharge | 费率版本、生效时间、费用计算依据 | 已产生费用保留对应费率快照 |
| OperationLog | 操作者/自动任务、事件、对象、时间、结果 | 成功业务日志与业务同事务；访问受限 |
| IdempotencyRecord | 操作者、动作、请求键、参数摘要、结果引用 | 同键同内容复用；同键不同内容拒绝 |

关系数据库是设计选择，具体产品未锁定；没有生成假装可直接执行的建库脚本。外键、唯一约束、检查约束、事务和必要索引在后续实现阶段落实。库存查询使用已生效容量减有效占用，不同时维护两个无校验的“剩余量真值”。

## 5. 非功能设计与验证边界

- 性能：按房型和日期建立查询索引，批量读取住宿区间，避免每个结果逐夜单独查询。后续以 1 万订单、20 人并发、100 次查询中至少 95 次成功且不超过 2 秒进行实测；设计阶段无达标结论。
- 安全：后端统一认证及资源范围过滤；每次写操作再次授权。密码采用成熟自适应加盐哈希；具体算法与参数在实现时核定。不允许将界面隐藏按钮当作授权保障。
- 隐私：演示只使用虚构信息。日志使用字段白名单，身份证不完整入日志；入住数据的保存期限仍待明确，不发明法定期限。
- 可靠性：款项是同数据库的模拟账本，使订单、库存、款项和成功日志可以同事务提交。若未来换真实支付，必须重新设计外部交易补偿，不能沿用同库原子性假设。
- 可恢复性：基于持久记录补扫任务及修改进度；已成功返回的提交不能依赖浏览器内存。重启、故障注入与并发验证尚待实现阶段执行。
