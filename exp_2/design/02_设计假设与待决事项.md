# 设计假设与待决事项

下列为 AI 提出的实验二候选方案，不是新访谈结果，不改变实验一需求状态，也不表示学生已经审阅同意。每条都必须在对应图、界面与后续实现中保持一致。

| ID | 来源 | 暂定方案或保留边界 | 影响与替代方案 |
| --- | --- | --- | --- |
| A01 | REQ-006 | 查询明确选择住宿总价；显示逐夜价格；人数按总容量校验，不自动替客人分配入住人数 | 可改为每晚价格筛选；需要调整 UI 文案及查询条件 |
| A02 | REQ-007、022 | 数据模型支持同酒店、同入住退房日期的多个房型明细，每项正整数间数；预订表单可先展示单房型实例，不将例子变成永久限制 | 如最终限定一单一间，保留明细仍可收敛；跨酒店或不同日期拆订单 |
| A03 | REQ-007、011 | 金额使用整数分；逐夜单价应用优惠后四舍五入到分，再乘间数求和；线上优惠不新增活动规则，使用已审核报价 | 舍入顺序影响金额；须与界面价格明细一致 |
| A04 | REQ-009 | 同房型竞争域内，同一库存被争用时按付款时间、订单 ID 排序；跨区间只限制同时可履行且确有冲突的更早在线订单。线下请求仍可在在线确认前取得房量 | 等时和跨区间排序为假设；不能把排序直接当已确认要求 |
| A05 | REQ-021 | 业务时区暂用 Asia/Shanghai；锁内取得服务端裁决时间；达到付款后 30 分钟时，接单入口先执行超时取消；并发取消与接单由先成功完成合法转换者决定 | 提交时间与受理时间差异影响退款；未来变更需更新所有时间边界 |
| A06 | REQ-007、021 | 在线未付款阶段以报价/结算草稿表达；成功模拟付款与创建待接单订单原子完成；草稿不占房，不在有效订单量中计算 | 草稿有效期和持久期限未定，先不承诺固定保留时间 |
| A07 | REQ-011、022 | 线下订单关联独立联系人快照，可无注册账号；工作人员完成模拟收款与逐夜占用后形成已确认订单 | 收款时点是暂定方案；顾客账号关联另作显式绑定，不按姓名自动认领 |
| A08 | REQ-014、021 | 修改先检查输入及报价，原单取消提交后再发起新付款；用修改进度记录恢复；原单不恢复 | 新价格或原退款额变化必须重新确认；不能用“失败回滚原单”掩盖业务风险 |
| A09 | REQ-017 | 延迟费在退房时按原定退房日 12:00 起算，12:00 整为零，ceil(超时秒数/3600)×费率；费率取入住时版本；无配置不自动编造金额 | 这是完整但未确认的候选；费用上限、部分退房、已入住续住的规则仍未定 |
| A10 | REQ-017 | 续住界面预留目标日期与后续可用性检查；与后续预订冲突时不得直接批准 | 续住计价与原订单更新形式待决，正式生效入口暂不定案；不删除该功能 |
| A11 | REQ-019 | 本酒店工作人员可发起应急停售；先封住受影响日期，生成影响清单；对已确认未入住订单全额退款并标记酒店原因取消；待接单无房订单全退 | 权限与终态为假设；已入住、部分住宿受影响进入人工处置，不擅自全退并终止在住客人的入住 |
| A12 | REQ-022 | 登录名作为演示注册标识；订单系统 ID 唯一；酒店内房号唯一；保留历史引用，停用代替物理删除 | 不通过“顾客+日期”唯一键禁止主动发起不同订单；保留期限待决 |
| A13 | REQ-023 | 日期筛选显式提供下单/付款/入住/退房类型；界面日期范围按日包含首尾，服务端转换为左闭右开时间区间 | 无匹配返回空列表；预订人按账号标识或联系人区分，不用同名认领 |
| A14 | REQ-024 | 演示统计明确展示口径：订单量按创建日期统计已付款线上单及确认线下单，含之后取消的单；修改产生新单单独计数。入住率暂用实际已使用房晚/可接待房晚。款项展示期间模拟收款减期间退款，单列超时费 | “净收款”不冒充会计收入；收入确认口径尚未定。可接待房晚分母、跨期处理必须在说明中标明；分母零显示“—” |
| A15 | REQ-004、005、021 | 审核可通过或驳回并附原因；驳回后工作人员修改再提交新版本；旧已生效内容继续有效 | 不增设多级审批；应急停售不依赖常规审核完成 |
| A16 | REQ-016、018 | 正常退房与未到店结束是不同事件；退房日 12:00 为未到店终止时点；提前退房退款、12:00 整正常退房边界不从未到店规则反推 | 具体房间待清洁仍需独立确认；提前退房不自动退款或释放所有后续夜 |
