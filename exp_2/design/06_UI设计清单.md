# UI 设计清单与实际交互范围（第二版）

## 入口和信息结构

顾客入口为 `prototype/index.html#home`。顶部固定“查找住宿”“我的订单”和登录身份；登录不改变导航结构。主任务依次是查房、房型详情、填写预订、模拟付款、等待确认、查看订单。

页脚“工作人员入口”进入独立工作区选择页。前台使用固定七项菜单；管理员使用概览、审核、全局订单、日志四项菜单。角色切换仅用于课程演示，不构成正式权限认证。

UI 编号留在本设计清单、截图文件名和独立 review.html 中。用户操作页面不显示审阅编号、状态选择器或技术设计长文。

视觉采用深绿色、暖白、少量价格强调色；正文清楚、字段分组，危险操作在确认弹窗内说明后果。照片为本地空间示意，来源在 `prototype/assets/SOURCES.md`。桌面宽度 1440、手机宽度 390 已检查，宽表在自身容器滚动。

## 设计组与可操作内容

以下编号延续需求映射。一个设计组可由列表、详情及弹窗共同完成，并非要求十八个互不相通的独立页面。

| 编号 | 设计内容 | 路由 | 当前前端交互 |
| --- | --- | --- | --- |
| U01 | 顾客登录与注册 | `#login` | 固定顾客导航；注册演示身份、演示账号登录；预订登录回跳保留表单。 |
| U02 | 房源查询 | `#results` | 校区、日期、人数、房型、住宿总价联合筛选；非法日期提示；无结果可清除筛选。 |
| U03 | 酒店与房型详情 | `#hotel/h1` | 照片与设施、行程摘要、逐房型总价；整段住宿可用后可选房。 |
| U04 | 填写预订与模拟付款 | `#checkout/h1/r1` | 联系人、电话、数量、逐晚价格与合计；确认规则后模拟付款，转入待接单。 |
| U05 | 我的订单 | `#orders` | 订单列表按状态筛选；详情给出进度、退款、修改及新旧单关联。 |
| U06 | 前台接单 | `#staff/orders` | 固定前台菜单；按付款顺序核对房量；确认后顾客端显示已确认。 |
| U07 | 线下订房 | `#staff/offline` | 填写联系人和住宿安排；核验校园卡后按公开价八折；费用确认后生成线下订单。 |
| U08 | 入住与退房 | `#staff/stays` | 入住核验与房间分配；正常退房转待清洁；续住先查后续房量。 |
| U09 | 房态与清洁 | `#staff/rooms` | 按具体房间展示可安排、在住、待清洁、故障；清洁完成可再次分配。 |
| U10 | 酒店资料维护 | `#staff/catalog` | 编辑酒店介绍和设施说明并提交；审核前对外资料保持原版本。 |
| U11 | 每日房量与价格 | `#staff/inventory` | 展示逐夜容量、占用、可售、价格；提交日期配置变更。 |
| U12 | 审核与费率 | `#admin/reviews` | 查看申请并通过或填写驳回原因；生效时检查最新确认占用；保存候选延迟费率。 |
| U13 | 经营概览 | `#admin/overview` | 展示订单量、模拟收款退款和净收款；独立全局查询页按酒店、日期、状态、关键词筛选。 |
| U14 | 操作记录 | `#admin/logs` | 展示实际演示操作的时间、操作者、动作、对象与结果。 |
| U15 | 无法接待处置 | `#staff/incidents` | 明确影响日期和房型，预览受影响订单，确认停售；未入住退款，在住列入人工处置。 |
| U16 | 付款成功待确认 | `#order/HB260001` | 付款后明确显示待酒店确认；说明超时、无房及主动取消的全退规则。 |
| U17 | 截止后取消确认 | `#order/HB260001` | 对已过入住日18:00的已确认订单，取消弹窗显示零退款；保留预订或确认取消。 |
| U18 | 修改后的新订单失败 | `#order/HB260004` | 展示修改后的新单失败、原单已取消；提供原单链接，提示原房不恢复。 |

18 张主图使用 `Uxx_normal.png` 文件名，以保持既有需求、UML 与报告引用稳定；`normal` 表示该设计组的主图，不表示 U17/U18 是业务成功状态。另有 8 张补充图：首页、手机首页、注册、无匹配查询、入住登记、全局订单查询、已确认订单详情、修改风险确认。实际文件与场景见 `checks/ui.json`。

U17 用昨日入住的确认订单构造截止后取消状态；U18 用相互关联的已取消原单和无房退款新单构造修改失败状态。其他截图使用初始虚构数据或实际点击进入弹窗。构造状态仅用于设计表达，不冒充后台业务发生记录。

## 原型边界

- 同一标签页通过 sessionStorage 保存虚构会话，刷新可继续操作；不是数据库持久化或跨设备账号系统。存储不可用时退化为内存演示。
- 付款、退款是本地状态变化，不调用外部服务。待接单不扣未来房量；确认时检查各夜，保留较早付款顺序提示。它不能证明真实并发正确。
- 接单超时在页面重新读取或操作时检查，不是运行于服务器的定时任务。未到店自动结束、后台重试和灾难恢复等仍按 UML 设计留待实验三。
- 日期查询当前限制1—30晚，入住人数可直接填写1—30之间的整数；按同房型容量向上取整计算所需间数，逐夜余房必须覆盖这些房间，报价与预算包含全部间数。预订自动填写最低所需间数，可增加但不可低于总人数所需容量。30人为当前原型上限，可后续调整；不是实验一新增已确认规则。混合房型组单仍留待后续实现。演示家庭套房配置为4间，以便体验7人及以上的多间房预订。
- 只演示正常入住和正常退房；为方便课堂体验允许提前办理。实际提前入住、提前退房、延迟费用和续住结算按待决项保留，不静默虚构规则。
- 全局查询目前按入住或退房日期、酒店、状态、联系人或订单号筛选。统计给出可核对的订单量和款项合计，未伪造没有完整历史数据的入住率；候选统计公式仍见 A13/A14。
- 酒店介绍与设施文本可提交审核；真实照片上传、账号管理、完整身份证信息、版本冲突、鉴权和数据脱敏需在实现阶段完成。
- 故障停售演示按所选房型全部影响处理；已入住与局部影响不自动结算，恢复可售需后续设计与实现。

`ui_catalog.json` 的 `planned_states` 是后续实现的异常设计目录，不能理解为全部已经执行。`design/05_验证场景.md` 的52项也是后续业务验证计划。实际已运行的前端任务检查以 `checks/ui_journeys.json` 为准。

## 如何复查

先从首页完成一次预订，再切换前台确认同一笔订单，最后回顾客端查看。随后检查取消金额、修改风险、入住退房与清洁、资料提交审核。编号页面能打开、没有横向溢出，仅是基础检查，不能代替任务路径和本人审阅。

源码直接维护于 `prototype/`；`tools/render_ui.cjs` 导出真实路由和弹窗。旧版与旧工具保存在 `work/archive_ui_v1/`，不再参与现行截图生成。
